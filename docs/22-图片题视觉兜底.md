# 22 图片题视觉兜底：从「抄字」到「看图」

> 2026-11-25 · 实测设备 Redmi M2101K9C / Android 17 / 服务端 Node v24.21.0
> 结论先说：**图片题现在两条路都能走** —— OCR 抄字（快、离线、免费）+ 视觉模型看图（能理解几何图形）。
> 分流判据已实测生效，`source=vision` 分支能正确答出几何题。

## 一、起因：air 问「有免费 OCR 吗，能不能直接把图片传给电脑」

两个问题都指向同一个事实：**图片本来就在传，只是没被当图片用**。

手机端 `handleWithOcr()` 截屏后把 base64 塞进 `/answer` 请求体，PC 端拿到后只做了一件事 ——
喂给 `OCR_URL`（`server/ocr_server.py`，RapidOCR）抄出文字，然后当纯文本走。

图片到了 PC，但**模型从没见过它**。这是能力缺口，不是传输缺口。

## 二、OCR 服务的真相：一直都在，只是没起

之前服务端日志里出现 `这一屏没有文字，图片题需要 OCR 服务（未配置）`，
误判成「OCR 没配」。实际情况：

| 事实 | 依据 |
|---|---|
| `OCR_URL` 默认值是 `http://127.0.0.1:18890/ocr`，非空 | `answer-server.mjs:47` |
| `server/ocr_server.py` 一直存在（4359 bytes） | 仓库内 |
| `start.cmd` 第 3 步会拉起它 | `start.cmd` |
| `rapidocr_onnxruntime` 已装 | `python -c "import rapidocr_onnxruntime"` 通过 |
| **没有任何进程在监听 18890** | `Invoke-RestMethod /health` 连接被拒 |

结论：**服务端代码没问题，是 OCR 服务没启动**。之前一直直接 `node server\answer-server.mjs`
（不经 `start.cmd`），所以第 3 步从来没执行过。

手动启动后立即验证：

```
GET http://127.0.0.1:18890/health
{"ok":true,"engine":"rapidocr_onnxruntime","ready":true}
```

真实 1080×2400 截图识别结果：22 行、320 字符，中文/英文/数字/URL 全部正确。

**RapidOCR 的性质**：本地 ONNX Runtime 推理，不联网、不花钱、无限量、约 4 秒/张（CPU）。

## 三、OCR 的天花板：几何图它抄不出来

实测那张几何题截图（直角三角形 + 边长标注 + 四个选项），OCR 输出是：

```
ABC BC = 90 AC = 3 GBC = 40 AB A5
```

- `∠C` 变成 `BC`
- `°` 丢了
- `AB 的长度` 变成 `A5`
- **三角形本身完全消失** —— 图形不在文字里

模型拿这串残渣猜，答出 `A 6`（错误，正解是 5）。

这不是 OCR 参数没调好，是**原理性上限**：OCR 只做「像素 → 字符」映射，
图形、几何关系、坐标系、电路连接、化学键，这些信息从来就不是字符。

## 四、视觉通道：插件早就支持，只是被关掉了

`@dmh2002/dsh-connect-qoder` 的图片能力是完整的，三处证据：

```js
// lib/host-heartbeat-_xDi4sbQ.js:244  —— 构造带图消息

  ...

// :296  —— 从 content 数组抽图
function extractMessageImages(message) {
  for (const part of content) {
    const iu = part.image_url;
    if (iu && typeof iu.url === "string") urls.push(iu.url);

// :427  —— 视觉开关写进请求体
```

而 `engine-qoder.mjs` 里写死了 `isVl: false`，且没有 images 参数 —— 整条视觉能力被短路。

## 五、实现：OCR 与视觉分流

### 5.1 `engine-qoder.mjs` —— 打开视觉通道

新增 `attachImages()`：把图片数组塞进**最后一条 user 消息**的 content。

```js
target.content = [
  { type: 'text', text },
  ...images.map((url) => ({ type: 'image_url', image_url: { url } })),
];
```

`qoderChat` 新增 `images` / `isVl` / `isReasoning` 参数：

```js
const hasImages = Array.isArray(opts.images) && opts.images.length > 0;
const isVl = opts.isVl ?? hasImages;      // 有图自动开视觉
```

关键约束：**图片必须和文字在同一条消息里**。`extractMessageImages` 只看 `role==='user'`
那条，单独发一条纯图消息会被丢掉。

### 5.2 `answer-server.mjs` —— 两个新函数 + 分流

`engineQoderVision(q, image)`：把原图以 data URI 交给视觉模型，
prompt 里额外说明「图里有几何图形、坐标轴、电路图、化学结构式时请结合图形作答」。

`shouldUseVision(q, ocrText)`：判断该不该烧图片 token。

```js
// 判据 1：压根没读到题干
if (!q || !q.stem) return true;

// 判据 2：有效汉字数不足（不是总长度！）
const han = (cleanOcrText(ocrText).match(/[\u4e00-\u9fa5]/g) || []).length;
if (han < minHan) return true;

// 判据 3：题干含图形提示词
if (/如图|下图|上图|图中|图示|坐标|曲线|电路|结构式|几何|阴影|面积|周长/.test(q.stem)) return true;
```

**为什么用「有效汉字数」而不是总长度**：OCR 噪声（时间、电量、KB/s、上一题残留）
都是短碎片，拼起来也不短，但有效信息为零。用长度判断会漏判。

分流位置在**缓存之后**：

```js
// solve() 内
const useVision = !!imageForVision && shouldUseVision(q, ocrText);
if (useVision) raw = await engineQoderVision(q, imageForVision);
else raw = await engine(q);
```

放缓存之后的原因：同一题第二次长按时命中缓存，不必再烧一次图片 token。

视觉失败时**自动退回文本引擎**，不让整题直接报错。

### 5.3 可配置项

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `ANSWER_VISION` | `1` | `0` = 全关，只走 OCR |
| `QODER_VL_MODEL` | 空 → 用 `QODER_MODEL` | 视觉模型 key |
| `ANSWER_VISION_MIN_HAN` | `8` | 有效汉字阈值 |
| `ANSWER_VL_TIMEOUT_MS` | `90000` | 视觉超时 |

`manager.mjs` 的 `buildEnv()` 已显式传递这四项（不传的话子进程只能吃 `DEFAULT_CONFIG`
常量，改 UI 不生效）。`index.html` 加了「视觉模型」「启用」「汉字阈值」三个控件。

## 六、实测证据

| 场景 | 判据 | 日志 | 结果 |
|---|---|---|---|

### 6.2 正确答案

```
POST /answer  {"image":"<geo3.png base64>","force":true}
```

`ZC` 是 OCR 把 `∠C` 读错的结果，但视觉模型看图后仍然答对 —— 这正是分流的价值。

## 七、顺带修掉的两个 bug

### bug 1 · loader 注册路径按 cwd 解析

```js
// 修复前 —— pathToFileURL('./') 是 cwd，不是文件位置
register('./dsh-resolve.mjs', pathToFileURL('./'));

// 修复后
register('./dsh-resolve.mjs', import.meta.url);
```

从仓库根跑 `node --import ./server/dsh-resolve-register.mjs ...` 时，
前者会去找 `<repo>/dsh-resolve.mjs`（不存在），抛 `ERR_MODULE_NOT_FOUND`，
而这个错误发生在 import 阶段，看起来像「插件依赖缺失」，极难定位。

### bug 2 · start.cmd 引号嵌套

```bat
rem 修复前：%PY% 可能是 "py -3"（含空格），内层引号提前闭合
start "cx-ocr" /min cmd /c "%PY% "%~dp0server\ocr_server.py""

rem 修复后：先 cd 再裸跑文件名
start "cx-ocr" /min cmd /c "cd /d "%~dp0server" && %PY% ocr_server.py"
```

并在启动后回查 `/health`，起不来就明说「图片题将退回视觉模型」，不再静默。

## 八、成本对比

| 方案 | 延迟 | 成本 | 能理解图形 |
|---|---|---|---|
| RapidOCR | ~4s | 0（本地） | ❌ |
| qoder 视觉 `dfmodel` | 3–7s | 图片 token | ✅ |
| 两者分流 | 文字题 4s / 图形题 7s | 只有图形题烧图片 | ✅ |

一张 1080×2400 PNG 转 base64 约 330KB，比 OCR 的纯文本贵得多 ——
所以**只在 OCR 判定读不出题干时才走视觉**，不是每题都走。
