# 手势重构与场景泛化构想

## 结论先行

三件事，难度递增：

| # | 需求 | 难度 | 工程量 | 风险 |
|---|---|---|---|---|
| 1 | Vol- 双击 → 退出弹窗（现为总开关） | 低 | 30 行 | 总开关要另找位置 |
| 2 | Vol- 长按 2s → 主动识别当前页 | 中 | 150 行 | **长按会把音量拉到底** |
| 3 | 泛化到非学习通场景 | 高 | 500+ 行 | 有些 App 根本读不到（见「天花板」） |

**推荐长按时长 2 秒 + 触发瞬间震动一次**。3 秒太慢，1.5 秒误触率高。

需求 2 是需求 3 的钥匙：**主动触发绕过了「猜这屏是不是题目」这个最难的判断**，用户手指一点，程序就不用猜了。这是本次构想里最有价值的部分。


| Xposed 主路径 | `xposed/VolKeyModule.java` | 95–122 |
| a11y 备路径 | `app/src/com/air/answer/ReaderService.java` | 170–206 |
| 接收端 | `app/src/com/air/answer/ToggleReceiver.java` | 25–43 |

**现有手势**：

| Vol+ ×2 | 切浮层显隐（读题继续） | `ReaderService:189` |

## 二、新手势表（建议）

| 手势 | 动作 | 说明 |
|---|---|---|
| Vol+ ×2 | 浮层显隐 | 不变 |
| **Vol- ×2** | **退出弹窗**（只隐藏浮层，读题继续） | 原为总开关 |
| **Vol- 长按 2s** | **主动识别当前页** | 新增 |
| Vol- ×3 | 总开关 | 新增，承接原双击的职责 |

**总开关必须有出口**，否则「应用暂停」这个状态在考试中途就没法用按键切了。三击是低成本方案（多按一下而已），也可以只留 App 界面按钮 + Xposed 广播。

> 待 air 定：三击保留总开关 / 总开关只留界面按钮。

## 三、长按检测：不能用 repeatCount

`KeyEvent.getRepeatCount()` 在长按时递增，但**递增间隔由 ROM 决定**（实测 HyperOS 约 50ms 一次，部分 ROM 会变），用它计时不可靠。

必须自己算时长：

```
ACTION_DOWN (repeatCount == 0)  → 记 downAt，起一个 2s 定时器
ACTION_DOWN (repeatCount > 0)   → 不处理（定时器在跑）
定时器到点（仍按住）            → 触发识别，标记 fired
ACTION_UP                       → 清定时器；若 fired 则不当作单击
```

### 状态机（Vol- 专用）

```
        DOWN#1
          │
          ▼
    ┌─ 按住 2s ────→ 长按：主动识别（吞掉后续，音量回滚）
    │
  UP#1 (< 500ms)
    │
    ├─ 无第二次 DOWN (500ms 内) ──→ 单击：正常调音量
    │
    └─ DOWN#2
         │
         ├─ UP#2 (< 500ms) ──────→ 双击：退出弹窗
         │
         └─ DOWN#3 (500ms 内) ───→ 三击：总开关
```

### 三个必须处理的坑

**坑 1：长按会把音量拉到底**

现在 `onKeyEvent` 返回 `false`，按键透传给系统，长按 2 秒 = 音量连降 20 格到静音。用户识别完发现手机没声了。

修法：长按触发后
1. 后续 repeat 事件 `return true` 吞掉
2. 触发瞬间把音量恢复到按下前的值（`AudioManager.setStreamVolume`，需要 `MODIFY_AUDIO_SETTINGS` 权限）

**坑 2：双击的第一下会被误判成长按起点**

定时器必须绑在「第一次 DOWN」上，但 UP 到达时要立刻取消。上面状态机已覆盖：`UP#1 (< 500ms)` 分支先取消定时器，再等第二次 DOWN。

**坑 3：Xposed 和 a11y 两条路径会重复触发**

现在两条路径各有一套 `lastVolDownDownAt`，都触发会执行两次。实测 HyperOS 只走 Xposed，但换 ROM 可能两条都走。

修法：Xposed 触发后 `setResult(null)` 吞掉事件，a11y 就收不到了；或者用一个静态标志位跨路径去重（不可靠，不同进程）。**推荐 Xposed 吞事件**。

## 四、主动识别通道

核心：**跳过所有「猜」的闸门，直接送**。

### 现在为什么会被闸门挡住

三道闸门，任一道不过就不作答：

| 闸门 | 位置 | 判据 |
|---|---|---|
| 1 | `ReaderService.looksLikeQuestion()` : 407 | 选项字母 / 分值 / `____` / 题号 |
| 2 | `ReaderService.isExamPage()` : 401 | `交卷\|答题卡\|上一题\|下一题\|剩余时间\|倒计时\|共N题` |
| 3 | `answer-core.looksLikeQuestion()` : 384 | 服务端再判一次 |

这三道全是**学习通考试页专用文案**。换成雨课堂、学习强国、某个培训 App 的测验页，闸门 2 直接不过 —— 轮询都不启动（`ReaderService:161`）。

### 主动识别怎么绕过

```
长按 Vol-
  → 新增 forceScan()
      ├─ 不看 isExamPage()
      ├─ 不看 looksLikeQuestion()
      ├─ 先试 a11y 文本（readAllWindows）
      ├─ 有图片节点 → 走 URL 直取
      ├─ 文本够长 → 直接 POST /answer {force:true}
      └─ 文本太少 → 截屏 OCR（这才是主力，因为陌生 App 的 a11y 树往往很烂）
```

服务端要加 `force` 参数：跳过 `EXAM_CHROME_RE` 和 `looksLikeQuestion`，只做最基础的噪声清洗，然后交给模型。

### 一个关键取舍

**主动识别默认走 OCR 还是走 a11y 文本？**

| | a11y 文本 | 截屏 OCR |
|---|---|---|
| 快 | 0ms 读树 | 3168ms（实测） |
| 准 | 结构完整（能分题干/选项） | 有噪声、可能漏行 |
| 覆盖 | 只对标准控件有效 | 任何能显示的都能读 |
| Flutter/RN/Canvas | **读不到** | 能读 |

建议：**先 a11y，读不到再 OCR**，两个都试。这也是现有 `attempt()` 的逻辑，主动识别只是把入口闸门拆了。

### 需要新增的入口

```java
// ReaderService 新增
public static void forceScanNow() { ... }   // 给 ToggleReceiver / Main 调用
```

`ToggleReceiver` 新增 `which = "scan"` 分支。

## 五、泛化：能到哪、到不了哪

### 能覆盖

| 场景 | 可行度 | 说明 |
|---|---|---|
| 其他考试 App（雨课堂、云班课、问卷星） | 高 | a11y 树标准，OCR 兜底 |
| 网页版测验（Chrome/Edge） | 高 | WebView a11y 树信息最全 |
| 纸质题拍照 | 中 | 需要相册选图 → OCR，是另一个入口 |
| 本地 PDF 习题 | 中 | 同上 |
| 网课视频里的题 | 低 | 需截当前帧，时序难对齐 |

### 天花板（诚实说）

1. **Flutter / React Native / Unity 自绘界面** —— a11y 树可能是空的或只有几个无意义节点。只能靠 OCR，且 OCR 对自绘字体的识别率会掉。
2. **游戏化答题**（答题闯关、限时 PK）—— 界面元素不断动画，OCR 抓到的帧可能是过渡态。
3. **题型判断仍是中文关键词** —— `answer-core.mjs:99` 的 `TYPE_WORDS` 硬编码了 18 个中文题型词。英文题（`Single Choice`）识别不了，会被当简答题。
4. **答案格式** —— 现在输出 `A` / `AB` / `对` / 填空文本。有些场景要的是拖拽排序、连线、画图，这套给不了。

### 泛化的三层改造

**第 1 层：拆掉硬编码闸门（必做，200 行）**

- `isExamPage()` 改成「学习通专用快路径 + 通用慢路径」
- 通用判据换成**结构特征**而非文案：`选项数 ≥ 2` + `存在至少 2 个长度 > 10 的文本块` + `不是纯导航`
- 服务端 `EXAM_CHROME_RE` 降级为「加分项」而非「必要条件」

**第 2 层：轮询策略（必做，100 行）**

现在只在 `isExamPage()` 为真时轮询。泛化后不知道是不是答题页，两个选择：

| 方案 | 代价 | 适用 |
|---|---|---|
| A. 用户手动开「泛化模式」，开了就全程轮询 | CPU 0.33% 单核（实测） | 推荐 |
| B. 内容变化才轮询（监听 a11y 事件） | 图片题换页不触发事件，会漏 | 不行 |
| C. 主动识别为主，轮询为辅 | 用户要按一下 | 最省电，但麻烦 |

推荐 **A + 长按主动识别并存**：泛化模式开着手不用按，不开就靠长按。

**第 3 层：多语言 / 多题型（可选，200 行）**

- `TYPE_WORDS` 加英文（`single choice` / `multiple choice` / `true or false` / `fill in the blank`）
- `OPTION_RE` 已经支持 `A.` `A、` `A)` `(A)`，够用
- 判断题 `JUDGE_TRUE/FALSE` 加 `Yes/No` `True/False`（已有 `true/false`）

## 七、建议的实施顺序

1. **先只做需求 1 + 2**（手势重构 + 主动识别），不动泛化。
   理由：主动识别本身就是泛化的最小可用版本 —— 用户按一下，程序不猜，直接读。先验证这条路在非学习通 App 上到底能读到什么。
2. 拿 3–5 个真实 App 试（雨课堂 / 问卷星 / 一个 Flutter 做的题库 App），记录 a11y 树和 OCR 结果的差异。
3. 根据实测数据再决定泛化怎么改 —— **别现在拍脑袋写通用判据**，很容易写成「什么都判成题目」。
4. 最后做多语言。
