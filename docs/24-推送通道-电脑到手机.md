# 24 推送通道：电脑 → 手机

> 2026-11-25 · 实测环境 电脑热点 10.75.124.158 / 手机 10.75.124.202
> 结论：**手机不监听端口，电脑无法主动连手机**。要做「电脑推手机」只能反过来 —— 手机来取。
> 已实现队列 + 长轮询，实测 815ms 送达。

## 一、为什么不能直接推

先测了物理链路：

```
ping 10.75.124.202        → 通
端口扫描 5555/8080/8888/18888/18889/18890/5037/27183
                          → 全部 closed
```

手机能 ping 通，但**没有任何监听端口**。查源码确认：

```bash
grep -r "ServerSocket\|HttpServer\|NanoHTTPD" app/src/
# 只有 Bus.java 的 Listener（进程内静态总线）
# 没有一处 ServerSocket
```

App 是纯客户端：`ReaderService` 用 `HttpURLConnection` 主动 POST 到电脑，
从不监听。所以现有架构是**单向**的（手机拉、电脑答）。

电脑要主动推，理论上三条路：

| 方案 | 可行性 | 代价 |
|---|---|---|
| 手机端起 ServerSocket | 要改 App + 重装 | 高，且 Android 后台服务限制多 |
| adb forward 隧道 | USB 必须连着 | 当前 `adb devices` 为空，不可用 |
| **手机长轮询来取** | **零改动手机端** | **已采用** |

长轮询的本质：手机发一个「挂住」的 HTTP 请求，电脑有消息就立刻返回，
没消息就挂 25 秒再空返回。对手机来说只是多一个 HTTP 请求，不需要开端口。

## 二、实现

### 2.1 服务端（`answer-server.mjs`）

三个路由：

```
POST /push           电脑推消息   body: {text, kind}
GET  /pull?since=N   手机来取（长轮询，最多挂 25s）
GET  /push           手机浏览器直接打开的接收页
```

队列结构：

```js
const PUSH_MAX = 200;
const PUSH_WAIT_MS = 25000;
let pushSeq = 0;
const pushQueue = [];      // {seq, text, kind, at}
const pushWaiters = [];    // {res, since, timer}
```

**为什么用队列而不是「一条消息配一个 waiter」**：长按连发时消息会叠，
队列保证不丢、且支持多个客户端各自按 `since` 增量取。

`pushAdd()` 推入后立刻叫醒所有挂着的 waiter：

```js
for (const w of pushWaiters.slice()) {
  const got = pushQueue.filter((m) => m.seq > w.since);
  if (got.length) pushFlush(w, got);
}
```

`pushWait()` 的三条退出路径都必须清理 waiter，否则泄漏：

```js
// 1. 有消息 → 立刻返回
// 2. 25s 超时 → 返回空数组（手机拿到空数组就再发一次，形成长轮询）
// 3. res.on('close') → 手机中途断开，清掉 waiter
```

第 3 条最容易漏：手机切后台、锁屏、断网都会触发 `close`，
不清理的话 `pushWaiters` 会一直涨。

### 2.2 答题结果自动进队列

`solve()` 出结果后顺手推一条：

```js
if (r.source !== 'none') {
  pushAdd(
    `${r.answer}\n\n[${r.source} · ${r.question?.type || '-'} · ${Date.now() - t0}ms]`,
    r.source === 'error' ? 'error' : 'answer',
  );
}
```

不推 `source=none`（那是「这屏不是答题页」，没信息量）。

这样手机浏览器开着推送页时，长按识别的答案会同时出现在浮层和浏览器里 ——
调试时很有用，能看到服务端到底回了什么。

### 2.3 手机端接收页

`GET /push` 返回一个自包含 HTML（2.2KB，无外部依赖）：

- 深色配色，等宽大字
- 每条消息带时间 + 序号
- `navigator.vibrate(60)` 新消息震动
- 断线自动重试（1.5s 后重来）
- 连接状态用圆点表示（绿=已连接，红=断开）

轮询循环就是递归调 `tick()`：

```js
async function tick(){
  try{
    const r = await fetch('/pull?since=' + since, {cache:'no-store'});
    const j = await r.json();
    if (j.items && j.items.length){
      for (const m of j.items) add(m);
      since = j.seq;
    }
  }catch(e){
    await new Promise(r => setTimeout(r, 1500));
  }
  tick();
}
```

## 三、实测

### 3.1 基本投递

```
推一条 → seq 递增 → since 拉得到 → 内容/kind 都对
```

### 3.2 长轮询唤醒（关键）

```
[13:44:57] 挂起 pull，3 秒后推送
[13:45:00] 返回，耗时 3007ms   ← 精确唤醒，没等满 25s
```

### 3.3 超时路径

```
[13:45:58.940] 起始 seq=216，挂起
[13:46:23.959] 返回，耗时 25018ms，items=0   ✅
```

### 3.4 多客户端广播

3 个长轮询同时挂起，推一条 → 3 个全部收到，耗时 516ms。

### 3.5 队列上限

连推 210 条 → `since=0` 只拉到 200 条，seq 单调递增到 216。
`pushQueue.splice(0, length - PUSH_MAX)` 生效，不会无限涨。

### 3.6 答题结果自动推送

```

推送队列: #645 [answer] C HTTP / [qoder · single · 1568ms]
```

## 四、怎么用

### 手机浏览器（最简单，验证用）

```
http://10.75.124.158:18888/push
```

打开就能收。电脑这边：

```powershell
Invoke-RestMethod 'http://10.75.124.158:18888/push' -Method Post `
  -Body '{"text":"你好手机","kind":"ok"}' -ContentType 'application/json'
```

### 接进 App（后续）

现在 App 里已有 `pollTick` 轮询循环（`ReaderService.java:394`，用于页面扫描）。
接推送只需要在同一个 tick 里加一次 `/pull` 请求，拿到消息后
`Bus.publishV2(...)` 就能走现有浮层显示路径 —— 不用碰网络层。

**注意**：`pollTick` 只在 `isExamPage()` 为真时启动（`:264`）。
要收推送得改成常驻，或者单独起一个轻量循环。这是下一步的事。

## 五、边界与遗留

- **队列在内存里**，重启即清空。这是有意的 —— 推送是「此刻的通知」，
  重启后补发旧消息没有意义。
- **`seq` 会随重启归零**。手机端如果缓存了旧的 `since`（比如 645），
  重启后所有 `seq` 都小于它，会一条也收不到，直到新消息的 seq 涨过 645。
  真实客户端应该处理：拿到 `seq` 比自己的 `since` 小就重置 `since=0`。
  当前接收页没做这个，重启后需要刷新页面。
- **没有鉴权**。`0.0.0.0:18888` 意味着同一网段任何人都能推消息、看消息。
  热点是私有的，当前可接受；接公网必须先加 token。
- **单条消息无大小限制**（受 `readBody` 的 4MB 上限约束）。
- 手机端 App 尚未接入推送，只验证了浏览器路径。
