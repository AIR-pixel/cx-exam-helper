# 23 代码审查：视觉兜底上线后的四个缺陷

> 2026-11-25 · 对 `2c81baa`（图片题视觉兜底）的自审
> 结论：**4 个缺陷，1 个 P0（会导致答案串题）**，全部已修 + 回归测试。

## 一、总览

| # | 级别 | 问题 | 后果 |
|---|---|---|---|
| 1 | **P0** | 空 stem 的图片题共用同一个缓存键 | **A 题的答案被喂给 B 题** |
| 2 | P1 | `shouldUseVision` 只数 `ocrText` 的汉字 | 文字题白烧图片 token |
| 3 | P1 | 视觉答案回写缓存时 source 记成 `engineMode` | `/stats` 来源分布失真 |
| 4 | P2 | `renderAnswer` 不校验选项下标边界 | 4 个选项的题渲染出 `F` |

另有两个**既有设计问题**（非本次引入），记录但不改：

- `qoderChat` 的 `timeoutMs` 只设 `err` 变量，不中断请求（见 §五）
- `detectImageMime` 对 WebP 的嗅探字符串不对齐（见 §六）

## 二、P0 · 空 stem 图片题撞缓存键

### 现象

`normalizeForHash` 只用「题干 + 选项」算哈希。图片题的题干在像素里，
a11y 抽不到，`q.stem` 是空串 —— 哈希就只剩选项。

实测：

```js
normalizeForHash({ stem: '', options: [] })        // 334359b9...
normalizeForHash({ stem: '   ', options: [] })     // 334359b9...  ← 同一个
normalizeForHash({ stem: '。，、', options: [] })   // 334359b9...  ← 同一个
```

两张**完全不同**的图片题，只要选项文字一样：

```js
// 都是 { stem: '', options: [传输层, 网络层, 数据链路层, 物理层] }
q1 key: b8e2dcaddb715ea1ad67fc653874931e
q2 key: b8e2dcaddb715ea1ad67fc653874931e
相同? true
```

### 后果

第一次答对 A 题后写入缓存；第二次遇到 B 题（选项恰好相同）直接命中，
把 A 题的答案当 B 题的答案返回。**用户看到的是一个确定的、格式正确的、错的答案** ——
比报错危险得多，因为没有任何信号提示它错了。

学习通题目选项高度模板化（「以上都对」「A 和 B」「不确定」），
这个碰撞不是理论风险，是必然发生。

### 修法

`normalizeForHash` 在空题干时返回 `null`，表示「不可缓存」：

```js
const stem = ...归一化...;
if (!stem) return null;   // 没有题干就没有去重依据
```

`AnswerCache.get/put/delete` 遇到 `null` 一律跳过：

```js
get(q) {
  const key = normalizeForHash(q);
  if (!key) return null;          // 图片题永不命中
  ...
}
put(q, answer, source) {
  const key = normalizeForHash(q);
  if (!key) return null;          // 图片题永不写入
  ...
}
```

`solve()` 里回写时打日志，便于观察：

```js
const wrote = cache.put(q, normalized, src);
if (!wrote) console.log('[cache] 空题干，跳过缓存写入');
```

### 取舍

图片题从此**永不命中缓存**，每次长按都要调一次视觉模型。这是正确取舍：
没有题干就没有去重依据，宁可多花一次 token，也不能返回别人的答案。

`geo3.png` 那张图不受影响 —— 它的 OCR 结果有完整题干（含「如图所示」），
stem 非空，照常缓存。实测首次 `source=vision`（4.7s），第二次 `source=cache`（1.5s）。

## 三、P1 · 汉字阈值取错源

### 现象

```js
// 修复前
const cleaned = cleanOcrText(ocrText || '');
const han = (cleaned.match(/[\u4e00-\u9fa5]/g) || []).length;
```

只数 `ocrText`。但 `ocrText` 在两种情况下是空的：

1. 图片题，OCR 确实没读出东西 ← 想判的就是这种
2. **文字题，a11y 已经读到完整题干，但 OCR 服务没起/超时** ← 误判

实测第 2 种：

```
stem 有效汉字数: 27
ocrText 为空时 shouldUseVision -> true     ← 误判
  期望 false（题干已经够好，不需要看图）
```

### 后果

每题白烧一次 330KB 图片 token，多等 3-7 秒，对纯文字题零收益。
而且 OCR 服务是独立进程（`start.cmd` 第 3 步拉起），它挂掉时
所有文字题都会退化成视觉题 —— 用户只会觉得「变慢变贵了」，找不到原因。

### 修法

取 stem 和 ocrText 的较大者：

```js
const countHan = (s) => (String(s || '').match(/[\u4e00-\u9fa5]/g) || []).length;
const hanStem = countHan(q.stem);
const hanOcr = countHan(cleanOcrText(ocrText || ''));
const han = Math.max(hanStem, hanOcr);
```

日志同时打出两个来源，排查时不用猜：

```
[vision] 有效汉字 0（stem=0 ocr=0）< 8，改走视觉
[vision] 有效汉字 27（stem=27 ocr=0）...   ← 不会再出现
```

## 四、P1 · 视觉答案的 source 标记错误

### 现象

```js
// 修复前
cache.put(q, normalized, (engineMode === 'openai' || engineMode === 'qoder') ? 'ai' : engineMode);
```

`engineMode` 是**启动时请求的引擎**，不是**实际出答案的通道**。
视觉分支和 `engineMode` 无关：

- `ANSWER_ENGINE=heuristic` + 走视觉 → 答案被标成 `heuristic`
- `/stats` 的 `bySource` 会把视觉答案算进 heuristic

### 修法

```js
const src = useVision ? 'vision' : ((engineMode === 'openai' || engineMode === 'qoder') ? 'ai' : engineMode);
```

实测写入后：

```
几何题缓存条目：19f473b0... src=vision hits=1
全部来源分布：ai: 11  echo: 1  heuristic: 3  vision: 1
```

## 五、P2 · 选项下标越界无校验

### 现象

`renderAnswer` 直接 `String.fromCharCode(65 + i)`：

```js
renderAnswer({ params: { selectedIndex: 5 } }, q4)  // → "F"
```

4 个选项的题渲染出 `F`。多选同理，`indicesJson: '[0,2,7]'` 会渲染出 `A ; C ; H`。

视觉模型看图数选项时比文本模型更容易越界（图里选项可能被截断、
可能有多列布局）。这是既有缺陷，但视觉路径放大了它。

### 修法

单选校验整数且在范围内，越界返回空串：

```js
if (!Number.isInteger(i) || i < 0 || (opts.length > 0 && i >= opts.length)) {
  console.error(`[render] selectedIndex=${p.selectedIndex} 越界（选项 ${opts.length} 个），丢弃`);
  return '';
}
```

多选过滤越界项，保留合法的：

```js
const valid = idx.filter((i) => Number.isInteger(i) && i >= 0 && (optsLen === 0 || i < optsLen));
if (valid.length !== idx.length) console.error(`[render] indices 越界 ...，已过滤`);
```

空渲染不再当有效答案返回 —— `solve()` 里加一道：

```js
if (!rendered) {
  console.error(`[render] 空答案 raw="..." type=${q.type} opts=${...}`);
  return { answer: '模型回答格式异常，请再按一次', source: 'error', ... };
}
```

否则手机端浮层显示空白，用户以为卡住了。

### 顺带改的 prompt

图片题常见：选项也画在图里，`q.options` 为空。此时 prompt 里没有选项列表，
模型不知道有几个选项。补一句：

```
选项也画在图里，请自己读出选项个数，index 从 0 开始按图中 A/B/C/D 顺序计。
```

## 六、既有问题（本次不改，记录）

### 6.1 `qoderChat` 的超时不中断请求

```js
const timer = setTimeout(() => { err = err || new Error(`qoder 超时 ${timeoutMs}ms`); }, timeoutMs);
await client.chatStream(...)   // ← 没有 signal，不受 timer 影响
clearTimeout(timer);
if (err) throw err;
```

`timeoutMs` 只能检测「跑完了但超时」，**无法中断进行中的请求**。
请求卡住时 `await` 永久挂起，外层 HTTP 也没有超时 —— 手机端断开后
服务端这个 Promise 永远挂着，内存不释放。

视觉路径更危险：图片请求更慢、更容易挂住。

修法需要给 `client.chatStream` 传 `AbortSignal`，要看插件是否支持 —— 留待单独处理。

### 6.2 `detectImageMime` 的 WebP 嗅探不对齐

base64 是 3 字节 → 4 字符，`UklGR` 只有 5 个字符，跨了编码边界。
`RIFF` 的 base64 实际是 `UklGRg==` / `UklGRiQ...`，所以 `startsWith('UklGR')`
能匹配，但理论上任意 `RIFF` 容器（如 WAV）也会被判成 WebP。

实际影响为零：`imageToBase64` 的来源只有 PNG 截屏和 `<img>` 的 targetUrl，
不会传 WAV。真要严谨就解出前 12 字节比对 `RIFF....WEBP`。

### 6.3 `attachImages` 会丢弃已有的 image part

```js
target.content = [{ type: 'text', text }, ...images.map(...)];
```

原 content 里如果已经有 `image_url`，会被整个覆盖掉。当前调用路径
（`engineQoderVision` 每次新建 messages）不会触发，但属于隐患。
