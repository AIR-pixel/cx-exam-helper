# 音量键实测诊断 + 题目识别卡死分析

> 2026-11-25 实测。设备 Redmi M2101K9C / HyperOS / Android 17，serial `5c1f78e2`。

## 结论先行

| 问题 | air 的观察 | 实测结论 |
|---|---|---|
| 单击就退出 | ✅ 正确 | **已确认并修复**。单击确实触发，原因是同一按键被两个 hook 各处理一次 |
| 上下键界限模糊 | ✅ 正确 | **已确认并修复**。冷却计时器 `lastFire` 是共享的，Vol+ 会吃掉紧接的 Vol- |
| 会不会卡住 | — | 有 4 个卡死点，下面逐个分析 |

## 一、单击就触发：根因

### 现象

```
adb shell input keyevent 24   # 单击 Vol+ 一次
→ [VolKey] double UP -> toggle overlay
→ [AnsToggle] overlay -> false
```

**一次物理按键，日志打的是 `double`。**

### 根因

模块同时 hook 了两个入口（`VolKeyModule.java:88-89`）：

```java
hookKeyMethod(pwm, "interceptKeyBeforeQueueing");
hookKeyMethod(pwm, "interceptKeyBeforeDispatching");
```

一次物理按下会**先后经过这两个方法**。原代码只靠时间窗口去重，逻辑是：

```java
boolean isDouble = now - lastUp <= DOUBLE_MS;   // 500ms
lastUp = now;
```

第一次进 `onKey`：`lastUp` 是 0，`now - 0` 是个极大值 → `isDouble = false`，**但 `lastUp` 已被写成 now**。
第二次进 `onKey`（约 140ms 后，另一个 hook）：`now - lastUp ≈ 140ms < 500ms` → `isDouble = true`。

**所以每次单击都被判成双击。**

### 实测证据

```
RAW interceptKeyBeforeQueueing    code=24 downTime=9630628
RAW interceptKeyBeforeDispatching code=24 downTime=9630628   ← 同一 downTime！
```

两次调用的时间戳差 **147ms**，线程号不同（26587 / 25420）。

### 为什么不能用时间窗口

| 方案 | 问题 |
|---|---|
| 30ms 窗口 | 挡不住 147ms 的间隔 |
| 200ms 窗口 | 会吞掉真实连按（人手最快约 100ms） |
| **`getDownTime()`** | ✅ 同一次按下必然相同，不同次必然不同 |

`getDownTime()` 是 `KeyEvent` 自带的字段，两个 hook 拿到的是**同一个事件对象**，所以 downTime 完全一致。这是唯一可靠标识。

### 修复

`xposed/VolKeyModule.java`：

```java
private static long lastDownTime = 0;

// 用 downTime 去重
if (downTime == lastDownTime) return;
lastDownTime = downTime;
```

## 二、上下键互相干扰：根因

### 现象

```
按 Vol+ 双击（触发 overlay 切换）
→ 300ms 内按 Vol-
→ Vol- 完全没反应
```

### 根因

`VolKeyModule.java:141-142`（原）：

```java
if (now - lastFire < COOLDOWN_MS) return;   // lastFire 是共享的
```

`lastFire` 只有一份，不分 keyCode。Vol+ 触发后写 `lastFire = now`，紧接着的 Vol- 在 600ms 内会被这行直接丢弃。

### 修复

按 keyCode 拆成两份：

```java
private static long lastFireUp = 0;
private static long lastFireDown = 0;

long lastFireThisKey = code == KeyEvent.KEYCODE_VOLUME_UP ? lastFireUp : lastFireDown;
if (now - lastFireThisKey < COOLDOWN_MS) return;
```

a11y 备路径（`ReaderService.java`）有同样的问题，同样修了。

## 三、修复验证

用 `input keyevent` 注入按键实测（需要 root，普通 `adb shell input` 会报 `SecurityException: INJECT_EVENTS`）。

| 测试 | 操作 | 期望 | 实测 |
|---|---|---|---|
| T1 | 单击 Vol+ ×1 | 0 | **0** ✅ |
| T2 | 单击 Vol- ×1 | 0 | **0** ✅ |
| T3 | 双击 Vol+（`input keyevent 24 24`） | 1 | **1** ✅ |
| T4 | 双击 Vol-（`input keyevent 25 25`） | 1 | **1** ✅ |
| T5 | 双击 Vol+ 后立刻双击 Vol- | 2 | **2** ✅ |

**注意**：`input keyevent` 每次启动 JVM 约 500ms，所以「分两条命令」发两次单击会被当成两次独立单击（间隔超 500ms）。必须用**单条命令连发**（`input keyevent 24 24`）才能模拟真实双击。

## 四、题目识别机制：怎么发现换题

### 现有链路

```
startPoll()  ──每 2500ms──┐
                          ▼
              readAllWindows() 读 a11y 树
                          ▼
              isExamPage() 判是不是考试页
                          ▼ 是
              scan() → attempt() ×6 重试（每 400ms）
                          ▼
              三道闸门全过 → POST /answer
                          ▼
              服务端返回 stableKey
                          ▼
              stableKey != lastScreenHash ? 渲染 : 跳过
```

**换题检测靠两样东西**：

1. **轮询**（`POLL_MS = 2500`）：每 2.5 秒读一次屏
2. **stableKey 去重**（`ReaderService:763`）：题干+选项的哈希，和上次相同就不重渲染

`stableKey` 而不是 `screenHash` 是关键设计 —— 滚动屏幕时 `screenHash` 会变，但 `stableKey` 不变，所以滚动不会触发重复请求。

### 换题怎么被发现的

```
轮询读到新内容 → stableKey 变了 → 渲染新答案
```

不是「检测到翻页事件」，而是「内容变了」。好处是不依赖任何 App 的翻页机制，坏处是**只能靠轮询频率兜底**。

## 五、四个卡死点

### 卡死点 1：`inFlight` 卡住（最严重）

`ReaderService:318`：

```java
if (inFlight) { deferredScan = true; return; }
```

`inFlight` 在 `handleText` / `handleWithImageUrl` / `handleWithOcr` 的 `finally` 里复位：

```java
} finally {
    inFlight = false;
    flushDeferredScan();
}
```

**风险**：如果 `askPC` 抛出未捕获的 `Throwable`（不是 `Exception`），或者线程被意外杀死，`finally` 不会执行 → `inFlight` 永久为 `true` → **后续所有扫描全部返回，永久卡死**。

当前 `askPC` 内部有 `catch (Exception e)`，但 `OutOfMemoryError` / `StackOverflowError` 这类 `Error` 抓不到。

**备案**：
- `inFlight` 加时间戳，超过 60 秒强制复位
- 或改成 `AtomicBoolean` + `compareAndSet` 超时重置

### 卡死点 2：`pollRunning` 停了不再启动

`startPoll()` 只在 `onAccessibilityEvent` 里 `isExamPage()` 为真时调用（`ReaderService:172`）：

```java
if (!pollRunning && isExamPage(readAllWindows())) startPoll();
```

`pollTick` 里如果 `isExamPage()` 变假：

```java
} else {
    Log.d(TAG, "poll stop: not an exam page");
    stopPoll();
    return;      // ← 不重新排下一跳
}
```

**风险**：翻页瞬间如果读到过渡态（内容还没渲染完），`isExamPage()` 可能为假 → `stopPoll()` → **再也不轮询**，除非用户手动切走再切回。

**备案**：
- `stopPoll` 前给 3 次宽限（连续 3 次为假才停）
- 或停掉后 5 秒再探一次

### 卡死点 3：重试链被 `scanGen` 取消后无人接手

`attempt(n, gen)` 开头：

```java
if (gen != scanGen) return;   // 这条链已被更新的扫描取代
```

`scanGen` 在每次 `scheduleScan` 时 `++`。如果短时间内触发多次 `scheduleScan`（`windowContentChanged` 一秒来好几次），旧链全部自杀，新链重新从 `attempt#1` 开始。

**风险**：如果 `windowContentChanged` 持续高频触发（比如某个动画一直在跑），每条链都活不到 `attempt#2` 就被下一代取代 → **永远读不到完整内容**。

**备案**：`scheduleScan` 加最小间隔（如 500ms 内的重复触发合并成一次）。

### 卡死点 4：图片题 URL 去重误锁

`handleWithImageUrl`（`ReaderService:594`）：

```java
if (url.equals(lastImageUrl) && !lastScreenHash.isEmpty()) {
    Log.d(TAG, "image url skip: same url, already answered");
    ...
    return;
}
```

**风险**：如果服务端对同一 URL 第一次返回了错误（但 `lastImageUrl` 已被写入，见 `:597`），后续同一张图会被永久跳过，直到换图。

实际上 `lastImageUrl` 只在成功路径写（`:597`，在 `stableKey` 判重之后），所以这个风险较低。但**如果 `stableKey` 恰好相同**（同一道题重看），会一直跳过。

**备案**：`lastImageUrl` 加时间戳，超过 10 秒允许重试。

## 六、主动识别（长按）的设计修正

按 air 的澄清，**这不是泛化模式，是一次性手动触发**：

```
长按 Vol- 2 秒 → 识别当前这一屏 → 出答案
松手后不再自动识别，直到用户再按一次
```

这个理解比原来的「泛化模式」简单得多，也更安全 —— **不会在别的界面乱识别**。

对应改动：

| 项 | 原构想 | 修正后 |
|---|---|---|
| 泛化模式开关 | 需要一个「泛化模式」持久开关 | **不需要**，删除 |
| 轮询 | 泛化模式下全程轮询 | **不轮询**，只在长按时读一次 |
| 服务端 `force` 参数 | 需要 | 仍需要（跳过闸门） |
| 工程量 | ~725 行 | **~450 行**（省掉泛化模式那部分） |

### 长按触发后的流程

```
长按 Vol- 2s
  → 震动一次（确认触发）
  → 读当前屏（a11y 树）
  → 有文本 → POST /answer {force:true}
  → 文本不足 → 截屏 OCR → POST
  → 渲染浮层
  → 结束。不启动轮询，不记住状态
```

### 仍然要处理的坑

**长按会把音量拉到底** —— 这个不变，仍需音量回滚。

## 三个实现坑（都实测踩过）

### 坑 1：UP 事件也被两个 hook 各处理一次

第一版只对 ACTION_DOWN 做了 `downTime` 去重，UP 没做。结果一次物理松手被算成两次 tap：

```
[VolKey] Vol- tap #1     13:54:50.514  线程 6594
[VolKey] Vol- tap #2     13:54:50.517  线程 6638   ← 相隔 3ms，同一次松手
[VolKey] Vol- x2 -> toggle overlay
```

单击立刻变双击，和原来那个 bug 一模一样。修法：UP 单独用 `lastUpDownTime` 去重
（不能和 DOWN 共用 `lastDownTime` —— 同一次按压的 DOWN 和 UP 的 downTime 相同）。

### 坑 2：`static final Handler` 在 `<clinit>` 里炸掉整个模块

```java
private static final android.os.Handler H =
        new android.os.Handler(android.os.Looper.getMainLooper());
```

LSPosed 日志：

```
E LSPosedFramework: Failed to load class com.air.skipmodule.VolKeyModule
E LSPosedFramework:   at com.air.skipmodule.VolKeyModule.<clinit>(VolKeyModule.java:72)
```

整个类加载失败，`handleLoadPackage` 根本没被调用，音量键完全不工作。
`<clinit>` 阶段调用系统服务风险太高。修法：改懒初始化 + try 包裹，
`handler()` 返回 null 时所有定时器操作静默跳过。

### 坑 3：双击/三击的判定方式

第一版用「上次时刻」两层时间差判断，状态互相污染，单击被判成双击。
改成计数器：每松手一次 `volDownTapCount++`，定时器醒来按最终值派发。
三击立即派发，双击等 `TAP_WINDOW_MS`（500ms）。

## 主动识别（长按）的实现

### 三道闸门必须同时绕过

| 位置 | 判据 | 陌生 App 的结果 |
|---|---|---|
| `ReaderService.looksLikeQuestion:428` | 选项≥2 或有题型词 | false |
| `ReaderService.isExamPage:422` | 交卷/下一题/剩余时间… | false |
| `answer-core.looksLikeQuestion:384` | 同上 + EXAM_CHROME | ok=false |

实测证据（长按触发时打的日志）：

```
AnsReader: FORCE scan: chars=144 isExamPage=false looksLikeQ=false
AnsReader: answer src=heuristic type=unknown ms=45 => 启发式引擎占位答案
AnsReader: OVERLAY[900x174] 启发式占位 · unknown · 45ms
```

`isExamPage=false` 说明普通路径在 `ReaderService:172` 就不会 `startPoll()`，
在 `attempt()` 里也会被 `!usable` 挡掉。长按路径直接跳到 `handleText`，三道闸门全绕。

### 服务端 force 透传

手机端 `askPC` 在 body 里加 `force:true`，服务端 `solve(text, structured, ocr, force)`：

```
[force] gate bypassed, send raw 14 chars to model
[answer] 3ms source=error type=unknown force=true
```

对比同一段文本 `force=false`：

```
[none] not a question page examPage=false candidate="用户名 忘记密码"
[answer] 1ms source=none type=- force=false
```

服务端在 `!structured.ok` 且 `force` 为真时，构造一个 `ok:true` 的 structured
（stem=整屏文本、options 从手机端抽的、type=unknown），走同一条 缓存→模型→归一化
流水线。不复制逻辑。

### 长按的副作用处理

按住 2 秒音量会掉到静音（实测 20 → 0）。修法：按下瞬间 `readMusicVolume()`
存下，触发后 `restoreMusicVolume()` 写回。日志：`volume restored to 20`。

震动反馈用 `VIBRATE_SERVICE`，40ms 单次。需要 `android.permission.VIBRATE`。

## 卡死点 ①② 的修复

### ① `inFlight` 永久卡住

`inFlight` 在各 `handle*` 的 `finally` 里复位，但 `finally` 只在「正常返回或
抛 Exception」时执行。`Error`（OOM / StackOverflow）让线程直接死掉，
`finally` 不执行，`inFlight` 永久 true。之后所有 `scan()` / `attempt()` /
`handle*()` 全部在入口 return，**永久静默**，只能杀进程。

修法：加 `inFlightSince` 时间戳 + `IN_FLIGHT_TIMEOUT_MS = 90000`，
`scan()` 入口调 `reclaimStuckInFlight()` 检测超时并强制复位。

```java
private boolean reclaimStuckInFlight() {
    if (!inFlight) return false;
    long age = System.currentTimeMillis() - inFlightSince;
    if (age < IN_FLIGHT_TIMEOUT_MS) return false;
    Log.w(TAG, "inFlight stuck for " + age + "ms, force reclaim");
    inFlight = false; inFlightSince = 0;
    Bus.publishStatus("上次请求超时，已恢复", "off");
    return true;
}
```

### ② 轮询永久停摆

翻页瞬间 a11y 树是过渡态，交卷/上一题/下一题 这些按钮可能暂时消失，
`isExamPage()` 返回 false。原代码直接 `stopPoll()` 且不再重排 ——
之后再也不轮询，用户必须手动切走再切回。

修法：连续 3 次（约 7.5 秒）都不是考试页才真停。

```java
pollMissCount++;
if (pollMissCount >= POLL_MAX_MISS) { stopPoll(); return; }
```

## 顺带修的 ③

`scheduleScan` 每次都 `++scanGen`，正在跑的重试链下一跳发现代数变了就自杀。
如果 `windowContentChanged` 高频触发（页面有动画/倒计时），每条链都活不到
`attempt#2` 就被取代，表现为「一直读不到完整内容」。
加 500ms 最小间隔，多余事件直接忽略。
